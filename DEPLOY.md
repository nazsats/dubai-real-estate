# Deployment guide

The app is two deployable pieces. **Vercel hosts the frontend only** — it can't run
the FastAPI backend, which is a long-lived Python server with a database connection
pool. The backend goes on a container host; the frontend then points at its URL.

```
   Vercel                        Render                      Supabase
┌──────────────┐   HTTPS    ┌──────────────────────┐    ┌────────────────────┐
│ Next.js app  │ ─────────▶ │  FastAPI backend     │ ──▶│  PostgreSQL        │
│ (frontend/)  │   + JWT    │  (backend/)          │    │  (+ storage later) │
└──────────────┘            └──────────────────────┘    └────────────────────┘
```

Three services. Deploy in this order — each step needs a value from the one before.

---

## 1. Database (Supabase)

Follow [docs/supabase-setup.md](docs/supabase-setup.md): create the project, then
copy the **Session pooler** connection string.

> ⚠️ Use the **pooler** host (`…pooler.supabase.com:5432`), not the direct
> `db.<ref>.supabase.co` one. The direct host is IPv6-only and Render cannot reach
> it — you'd get connection timeouts with no obvious cause.

Keep the `postgresql://…` prefix; the app converts it to the async driver and
disables the prepared-statement cache so it works through the pooler
([db.py](backend/app/db.py)).

---

## 2. Backend (Render blueprint)

[`render.yaml`](render.yaml) deploys the API with production env vars already set.

In Render: **New → Blueprint → select this repo**. It reads `render.yaml` from the
repo root and prompts you for the three values that can't live in git:

- `DATABASE_URL` — the Supabase pooler string from step 1
- `ANTHROPIC_API_KEY` — from [console.anthropic.com](https://console.anthropic.com/settings/keys)
- `CORS_ORIGINS` — you don't have the Vercel URL yet. Put
  `http://localhost:3000` in for now and correct it in step 4.

`SECRET_KEY` is generated by Render automatically and stays stable across
redeploys. Region defaults to `singapore`, the closest Render offers to the UAE.

> **Free tier caveat:** free Render web services sleep after 15 minutes idle, so
> the first request after a quiet spell takes ~30s. Supabase free projects pause
> after a week of inactivity but can be resumed. Fine for a demo — upgrade before
> onboarding a paying agency.

### Doing it manually instead

Any container host works — `backend/` also ships a [Procfile](backend/Procfile)
and `.python-version`. Point the host at root directory `backend`; it will detect
the [Dockerfile](backend/Dockerfile). Without Docker:

- Build: `pip install -r requirements.txt`
- Start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`

### Environment variables

Already set for you by the blueprint — this is the reference if you deploy by hand:

| Variable | Value | Notes |
|---|---|---|
| `ENVIRONMENT` | `production` | **Turns on the startup safety checks** |
| `DATABASE_URL` | Supabase pooler URL | must be the `pooler.supabase.com` host |
| `ANTHROPIC_API_KEY` | `sk-ant-…` | [console.anthropic.com](https://console.anthropic.com/settings/keys) |
| `SECRET_KEY` | `openssl rand -hex 32` | signs login tokens — must be long and random |
| `CORS_ORIGINS` | `https://your-app.vercel.app` | exact origin, **no trailing slash** |
| `SEED_DEMO_DATA` | `false` | keeps 2,000 fake listings out of your real DB |
| `DEBUG` | `false` | |
| `ENABLE_DOCS` | `false` | hides `/docs` publicly; set `true` while testing |
| `RAPIDAPI_KEY` | *(optional)* | only needed for Bayut listing imports |

With `ENVIRONMENT=production` the app **refuses to boot** if the secret key is the
shipped default, the database is SQLite, CORS is empty or `*`, or debug is on. That
is deliberate — a bad boot is far cheaper than forged login tokens or a database
that disappears on your next deploy.

You won't have the Vercel URL yet on the first deploy. Put a placeholder in
`CORS_ORIGINS`, finish step 3, then come back and set the real value.

The health check path is **`/health`** (liveness — no database call, so a brief DB
blip won't cause the host to restart a healthy app). `/health/ready` is the one that
reports database connectivity.

When the service is live, copy its URL — something like
`https://dubai-broker-api.onrender.com`. Check it works:

```bash
curl https://dubai-broker-api.onrender.com/health/ready
# {"status":"ready","database":"connected","properties":0}
```

## 3. Frontend (Vercel)

Import the repo, then:

- **Root Directory**: `frontend` ← easy to miss, and nothing works without it
- **Framework preset**: Next.js (auto-detected)
- **Environment Variable**: `NEXT_PUBLIC_API_URL` = the Render URL from step 2 —
  no trailing slash

[`frontend/vercel.json`](frontend/vercel.json) is picked up automatically and adds
standard security headers (HSTS, nosniff, clickjacking protection).

`NEXT_PUBLIC_*` values are **baked in at build time**, not read at runtime. If you
change it later you must redeploy for it to take effect. If it's missing entirely,
the app now says so plainly instead of silently trying to reach `localhost:8000` on
the visitor's own machine.

---

## 4. Connect the two

1. Copy the Vercel URL, set it as `CORS_ORIGINS` on the Render service, redeploy.
2. Open `https://your-app.vercel.app` and sign up a new agency.
3. Verify: create a lead → open it → run **Match properties**.

`ALLOW_VERCEL_PREVIEWS=true` (the default) also accepts Vercel's per-branch
`*.vercel.app` preview URLs, so preview deploys work without re-listing each one.
Set it to `false` if you'd rather allow only the exact production origin.

### If something breaks

| Symptom | Cause |
|---|---|
| "Cannot reach the server at …" | `NEXT_PUBLIC_API_URL` wrong or missing — fix it and **redeploy** (build-time value) |
| Requests blocked by CORS in the browser console | `CORS_ORIGINS` doesn't exactly match your Vercel origin, or has a trailing slash |
| Render deploy fails at startup | Read the logs — the production guard prints exactly which setting is wrong |
| `getaddrinfo failed` on startup | Supabase's direct host is IPv6-only. Use the pooler host **and** the `postgres.<ref>` username |
| `tenant/user … not found` | Right pooler, wrong region or `aws-0` vs `aws-1` prefix. Copy the string from the dashboard |
| "too many connections" | `DB_POOL_SIZE` + `DB_MAX_OVERFLOW` × workers exceeds your Supabase plan |
| First request takes ~30s | Free Render instance waking from sleep |
| AI calls return 429 | Per-agency rate limit (`AI_RATE_LIMIT_PER_MINUTE`, default 15/min) |

## Post-deploy checklist

- [ ] `GET /health` returns `{"status":"healthy"}`
- [ ] `GET /health/ready` reports `"database":"connected"`
- [ ] Signup works from the deployed frontend (proves CORS is right)
- [ ] AI search returns results (proves the Anthropic key works)
- [ ] `/docs` is not publicly reachable (`ENABLE_DOCS=false`)
- [ ] Set a spend limit in the Anthropic console

## Known gaps before this is a real product

These are deliberate scope calls, not bugs — but know them before onboarding a
paying agency:

- **The demo account is seeded on first boot.** With `SEED_DEMO_DATA=false` it is
  not created, so create your own agency via signup. Never ship `demo@demo.ae` /
  `demo12345` to production.
- **Tenant isolation is application-level only.** Every query filters on
  `agency_id`, but there's no Postgres Row-Level Security, so a single missed
  filter in a future route would leak data across agencies.
- **Rate limiting is per-process and in-memory.** Run more than one worker and the
  effective AI limit multiplies. Needs Redis to be accurate.
- **`AUTO_CREATE_TABLES=true` creates tables but never alters them.** The moment
  you change a model you need a real Alembic migration — `alembic/versions/` is
  currently empty.
- **No automated tests**, so there is nothing catching a regression on deploy.
